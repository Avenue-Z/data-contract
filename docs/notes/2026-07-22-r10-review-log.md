# R10 format-versioning — review log

Companion to
[`docs/superpowers/specs/2026-07-22-r10-format-versioning-design.md`](../superpowers/specs/2026-07-22-r10-format-versioning-design.md).
**Not needed to implement it.** This is the record of what three review rounds caught, kept out of
the spec so the spec stays a build document.

Each round independently re-ran the spec's pasted evidence. All of it reproduced, every time. Every
defect below is something running the code does not check — which is the through-line worth keeping.

## Round 1 — naming and enumeration

- The new key was called `apiVersion`, following the R10 risk row. `odcs.py:84` already emits that
  key into the ODCS document meaning *the ODCS standard version*, and `to_odcs` takes a `Contract` —
  so `"apiVersion": contract.apiVersion` would have looked natural. Bounded, not latent: `to_odcs`
  builds its dict key by key, and the vendored ODCS enum excludes `v1`, so the wrong wiring fails
  `validate_odcs`. Renamed to `format_version` (spec §4.3).
- The stronger objection surfaced only on inspection and review had not raised it: all eighteen keys
  across the four models are lowercase or snake_case, so `apiVersion` would have been the sole
  camelCase key. That holds even without the collision.
- The edit-site table omitted `resolver.py`, which calls `Schema.from_yaml` **twice** and is
  therefore on the new exception's propagation path (spec §11.1).

**Lesson:** the parent spec's three revisions were all unverified *behavior*, fixed by running the
code. Here the code was run and the design was still wrong. *"Does this name already mean something
else in this repo?"* and *"what else calls this function?"* are grep questions, not runtime
questions. **An evidence discipline aimed only at execution will pass a design that collides with
the codebase it is being added to.**

## Round 2 — the direction the control does not run in

- `SUPPORTED_FORMAT_VERSIONS` and "refusal is total" described how a reader *rejects* a version. The
  document never said how one *accepts two* — the only path Control B ever actually takes, since the
  refusal exists to be rare. Spec §4.4 now specifies it, rejecting the obvious reading (branch on the
  changed key) in favour of normalizing on read.
- §4.3's "`format_version` is not exported to ODCS" was an assertion with no check — the spec's own
  diagnosed defect, relocated from behavior to policy, inside the section that diagnoses it. Promoted
  to criterion 13, where the enforcement turned out to be pre-existing and free.

**Lesson:** **verification pressure lands on the paths a design describes, so the gap opens where it
describes nothing at all.** Every claim in §4 was verified; the accept path had no claim to verify,
so nothing pointed at it.

## Round 3 — the fix for round 2 was itself half-specified

- **Two jobs, one name.** §4.4's "the models only ever implement the newest format" contradicted §4's
  model-level validator over the supported set. If the model accepts `v1`, then after an upcast you
  hold a v2-shaped object stamped `format_version: v1` and every consumer reading that attribute is
  misinformed. If it accepts only `v2`, the constant is not the reader's supported set. Same fault
  reached the field default and the rejection authority. Split into `READABLE_FORMAT_VERSIONS` and
  `CURRENT_FORMAT_VERSION` (spec §4.5). Both are `"v1"` today, which is why nothing looked wrong.
- **The operator never saw the message.** `cli.py:46` returns `exc.errors()[0]["msg"]` — first error
  only, and `extra_forbidden`'s `msg` carries no `loc`. Reproduced against a version-skewed file with
  strict keys applied: `contract lint` printed `Extra inputs are not permitted` and nothing else. No
  key names, no count (two unknown keys, one reported), no upgrade hint. **Every criterion in the
  spec was green in that state.** Fixed by giving `ContractFormatError` an attribute surface and
  adding criterion 14 (spec §5.2.1).
- Criterion 12 ("no pre-existing test changed") contradicted §11's `FROZEN_SURFACE` 5 → 6 row.
- §3.1 measured blast radius in this repo, where no authored file that matters lives.
- `cli.py:66` has no handler at all; §11.1 pointed it at §5.4, which only covers `_load_failure`.
- `consuming-repo-setup.md` documents the authored format for authors and was scoped to a pin bump.

**Lesson:** round 2's fix specified the accept path and left the *render* path unspecified — the
same failure one section later, which is round 2's own lesson coming true against the document that
recorded it. A criterion that asserts on an exception object does not cover what an operator reads;
those are two different surfaces, and only one of them is what the feature is *for*.
